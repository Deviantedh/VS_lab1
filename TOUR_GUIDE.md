#  Руководство пользователя и Тур по Системе управления сотрудниками

Добро пожаловать в проект! В этом руководстве подробно расписано, как запустить приложение, как проверить все функции через интерфейс Swagger UI и какие данные отправлять на каждом шаге.

---

##  1. Быстрый запуск

### Шаг 1.1: Запуск Docker Desktop
Убедись, что на твоём компьютере запущено приложение **Docker Desktop** (значок кита в статус-баре активен).

### Шаг 1.2: Запуск базы данных
В терминале внутри папки `lab1` выполни команду:
```bash
docker compose up -d postgres
```
*PostgreSQL 16 поднимется в фоновом режиме на порту `5432`.*

### Шаг 1.3: Запуск приложения в IntelliJ IDEA
1. Открой проект `lab1` в IntelliJ IDEA.
2. Найди класс: `src/main/java/portal/Lab1Application.java`.
3. Нажми зелёную кнопку **Run** рядом с методом `main`.
4. При старте Spring Boot автоматически подключится к PostgreSQL, и Flyway создаст все таблицы и начальные роли.

>  **Альтернатива (запуск всего в Docker без IDEA):**  
> `docker compose up --build` — соберёт и запустит приложение и базу в двух контейнерах.

### Шаг 1.4: Остановка Docker
Когда закончишь работу:
* `docker compose down` — штатная остановка и удаление контейнеров (данные в БД сохраняются в volume).
* `docker compose stop` — временная приостановка контейнеров.
* `docker compose down -v` — полная остановка с очисткой томов (полный сброс БД до чистой).

##  3. Пошаговый тур по сценариям системы

Пройди по шагам ниже, нажимая **Try it out** $\to$ вставляя JSON $\to$ **Execute**.

---

### Шаг 1: Создание организации (Компании)
* Секция: **`Companies`**
* Запрос: **`POST /api/companies`**
* Тело запроса:
```json
{
  "name": "Сеть городских кофеен"
}
```
* **Ожидаемый ответ:** `201 Created`, получен объект с `"id": 1`.

---

### Шаг 2: Создание филиала (Точки)
* Секция: **`Branches`**
* Запрос: **`POST /api/branches`**
* Тело запроса:
```json
{
  "companyId": 1,
  "name": "Филиал на Петроградской",
  "address": "Каменноостровский пр., 12",
  "phone": "+78121112233",
  "isActive": true
}
```
* **Ожидаемый ответ:** `201 Created`, получен филиал с `"id": 1`.

---

### Шаг 3: Создание должности в справочнике
* Секция: **`Positions`**
* Запрос: **`POST /api/positions`**
* Тело запроса:
```json

  "title": "Старший специалист"
}
```
* **Ожидаемый ответ:** `201 Created`, должность с `"id": 1`.

---

### Шаг 4: Регистрация нового сотрудника

* Запрос: **`POST /api/employees`**

}
```

---

### Шаг 5: Назначение сотрудника на филиал и должность (Связь M:N с доп. полями)

```

* Проверь историю сотрудника: вызови **`GET /api/employees/1/assignments`**.

---

### Шаг 6: Создание пользователя (Учетной записи) с ролью 0..3

### Шаг 8: Создание плановой смены в расписании

---

### Шаг 9: Проверка требования ТЗ — Пагинация с заголовком X-Total-Count
* Секция: **`Shifts`**
* Запрос: **`GET /api/shifts`** (нажми Execute с параметрами по умолчанию `page=0`, `size=20`).
* **Обрати внимание на блок Response Headers:**
  * Заголовок **`X-Total-Count: 1`** — точное количество записей в базе данных!
  * Тело ответа — чистый JSON-массив смен.

---

### Шаг 10: Проверка Транзакционного сценария №1 — Назначение на смену
* Секция: **`Shifts`**
* Запрос: **`POST /api/shifts/1/employees`**
* Тело запроса:
```json
{
  "employeeId": 1
}
```
* **Ожидаемый ответ:** `200 OK`, сотрудник добавлен в список `assignedEmployees`.
* **Проверка аудит-лога:** вызови **`GET /api/shifts/1/logs`** — увидишь запись со статусом `ASSIGNED`.
* **Проверка защиты от дублирования:** нажми **Execute** ещё раз с тем же телом — сервер вернёт понятную ошибку `409 Conflict`: *«Сотрудник Иван Смирнов уже назначен на эту смену»*.

---

### Шаг 11: Учёт фактического времени (ФАКТ) и Бесконечная лента (Slice)
* Секция: **`Attendance`**
* Сотрудник пришел на работу (Check-In):
  * Вызови **`POST /api/attendance/check-in`**:
    ```json
    {
      "employeeId": 1,
      "shiftId": 1,
      "comment": "Прибыл на рабочее место"
    }
    ```
  * Ответ: `201 Created`, зафиксировано `actualStart`.
* Проверка требования ТЗ — Бесконечная лента (Slice):
  * Вызови **`GET /api/attendance`**.
  * **Ответ:** объект с полями `content` и `hasNext: false` — пагинация работает без вызова тяжелого `count(*)`.
* Сотрудник уходит со смены (Check-Out):
  * Вызови **`POST /api/attendance/1/check-out`**:
    ```json
    {
      "breakMinutes": 45,
      "comment": "Смена успешно завершена"
    }
    ```
  * Сервер автоматически заполнит `actualEnd` и пересчитает `lateMinutes` (опоздание) и `overtimeMinutes` (переработку).

---

### Шаг 12: Проверка Транзакционного сценария №2 — Заявка на отпуск и отмена смен
1. Создаем смену на дату отпуска:
   * **`POST /api/shifts`**: создай смену на дату `"2026-09-28"` и назначь на неё сотрудника ID=1 через `POST /api/shifts/2/employees`.
2. Подаем заявку на отпуск:
   * **`POST /api/requests`**:
     ```json
     {
       "employeeId": 1,
       "type": "VACATION",
       "requestData": "{\"dateFrom\": \"2026-09-28\", \"dateTo\": \"2026-10-05\"}"
     }
     ```
   * Получена заявка с ID=1 в статусе `PENDING`.
3. Одобряем заявку (HR / Руководитель):
   * **`POST /api/requests/1/process`**:
     ```json
     {
       "status": "APPROVED",
       "processedById": 1,
       "resolutionComment": "Отпуск согласован"
     }
     ```
4. **Что произошло в транзакции автоматически:**
   * Заявка переведена в `APPROVED`.
   * В календаре отсутствий (**`GET /api/absences`**) появилась запись об отпуске сотрудника.
   * Сотрудник **автоматически снят** со смены от `2026-09-28`, и в лог смены записано действие `REMOVED`!
