КОНЦЕПЦИЯ:
Название концепта: Внутренний корпоративный портал и система самообслуживания сотрудников (для сетей кофеен, пекарен или мини-бизнеса).
Суть продукта: Автономная веб-система, которая разворачивается на локальном сервере компании (в подсети заведений). Сотрудники заходят в неё через браузер с любого планшета на кассе или со своего телефона, а руководство и HR управляют сетью через расширенный кабинет из офиса.
Что доступно рядовому сотруднику (бариста, пекарь, линейный персонал):
Личный профиль: просмотр своих данных, привязки к конкретной точке/филиалу и должности.
График работы: просмотр расписания смен (своих и общих по точке) в виде удобной ленты.
Подача заявок в офис:
Заявка на плановый отпуск или отгул с выбором дат;
Заказ справок (2-НДФЛ, справка с места работы);
Запись/отметка о прохождении медосмотра или диспансеризации (актуально для общепита).
Трекинг статуса: отслеживание решения по заявкам (на рассмотрении, одобрено, отклонено с комментарием).
Что доступно управляющему филиалом (менеджеру точки):
Управление сменами: создание графика работы на неделю вперед, назначение сотрудников на конкретные дни и временные слоты.
Табель и учет времени: отметка фактической явки сотрудника на смену и фиксация отработанных часов (полезно при опозданиях или переработках).
Контроль доступности: видимость того, кто из ребят на смене, а кто находится на больничном или в отпуске.
Что доступно HR-специалисту и администратору (офис):
Оргструктура сети: добавление новых заведений/точек, управление справочником должностей.
Управление персоналом: заведение новых сотрудников, изменение статусов (активен, в отпуске, уволен), перевод людей между филиалами сети.
Единый центр обработки заявок: входящий поток обращений от всех сотрудников сети с возможностью одобрить или отклонить запрос в один клик.
Аналитика и метрики: базовые сводки — сколько людей работает на точках, статистика по отработанным часам, перегрузкам и закрытым заявкам.
Почему это удобно как готовый IT-продукт:
Коробочное решение: система собирается и поднимается в пару команд через Docker, не требует дорогой облачной инфраструктуры и живет внутри локальной сети бизнеса.
Минимум бюрократии: линейный персонал больше не пишет бумажные заявления на отпуск или справки в мессенджерах — весь документооборот оцифрован в одном месте.

Формально у всех модулей есть доступ к одной БД, но лучше, чтобы каждый модуль работал в основном со своими таблицами через свои Repository.
Например:
Employee Service → employees, positions
Branch Service   → branches
Schedule Service → shifts, shift_employees
Request Service  → requests
Work Time Service → фактические данные рабочего времениА когда одному модулю нужны данные другого, он обращается к его сервису, а не начинает напрямую лазить в его Repository.
Это намного чище и потом сильно упростит переход к микросервисам.

Один функциональный модуль
Controller
Принимает HTTP-запрос от клиента.
Spring автоматически превращает JSON в Request DTO.
Запускает валидацию входных данных.
Передаёт Request DTO + необходимые параметры в Service.
Получает от Service Response DTO.
Возвращает клиенту HTTP-статус + JSON.
HTTP → Request DTO → Service → Response DTO → HTTPDTO
Request DTO — что клиент может прислать.
Response DTO — что мы хотим вернуть клиенту.
DTO не работает с БД.
DTO не содержит основной бизнес-логики.
Service
Получает Request DTO от Controller.
Выполняет всю бизнес-логику.
Проверяет бизнес-правила.
При необходимости вызывает другие Service внутри монолита.
Через Mapper получает/создаёт Entity.
Передаёт Entity в Repository.
Получает Entity обратно.
Через Mapper превращает Entity в Response DTO.
Если что-то не так — бросает Exception.
Request DTO
    ↓
Service
    ↓
бизнес-логика
    ↓
Mapper
    ↓
Entity
    ↓
RepositoryMapper
Преобразует:
Request DTO → Entity
Entity → Response DTOСам по себе не работает с БД.
Сам по себе не занимается бизнес-логикой.
Обычно Mapper отдельный для каждого модуля, а не один общий на всё приложение, потому что Employee и Shift преобразуются по-разному.
Entity
Обычный Java-класс, связанный с таблицей БД через JPA.
Описывает данные, которые хранятся в БД.
Содержит связи между сущностями.
Именно с Entity работает JPA/Hibernate.
Java Entity ↔️ таблица БДRepository
Получает Entity или параметры запроса.
Работает с БД через Spring Data JPA/JDBC.
Делает:
find
save
update
deleteМожет содержать специальные запросы.
Не должен решать бизнес-правила.
Enum
Хранит фиксированный набор значений.
Например:
EmployeeStatus:
ACTIVE
SICK
VACATION
DISMISSEDВ БД хранится как строка.
